我上一个博客跑了三年 WordPress。它工作得很好，直到我每篇文章都要等三秒才能打开，直到主题更新把我精心调的排版全打乱，直到我发现自己在备份数据库的时间比写作还多。

于是这次重建，我只定了三条硬要求：打开要快、内容要能带走、维护成本接近零。

## 为什么不选动态 CMS

动态 CMS 的痛点是结构性的：每次访问都要经历 PHP 执行、模板渲染、数据库查询三步。就算装了缓存插件，也只是把这三步的结果提前存一份。对于个人博客这种「一年改版两次、每天更新一篇」的使用频率，这套机制完全是过度设计。

静态站点的逻辑反过来：写文章的时候把 Markdown 编译成 HTML，访问的时候只是把文件发出去。没有数据库，没有运行时，没有插件冲突。

## 为什么是 Astro

同期可选的静态生成器很多，Hugo、Hexo、Next.js 静态导出都行。我选 Astro 有三个具体理由：

1. **默认零 JS**。Astro 页面默认不向浏览器发送任何 JavaScript，只有你显式声明需要交互的组件才会带上脚本。博客 99% 的内容是阅读，这一点很关键。
2. **内容集合（Content Collections）** 自带 frontmatter 的 Schema 校验。分类、标签、是否付费这些字段写错了，构建时直接报错，而不是上线后才发现。
3. **改动成本低**。一个 `.astro` 文件里可以同时写前端结构和服务端逻辑，改版时不用在多个配置文件之间来回跳。

代价是学习曲线：Astro 的组件语法和 React 不一样，`set:html`、`Fragment` 这类指令需要一点时间适应。但如果你只写博客，用到的东西很少。

## 为什么托管在 Cloudflare

静态站点可以放在任何地方，我选 Cloudflare Pages 是因为三件事同时成立：

- **免费额度够用**：个人博客的流量远低于免费套餐上限。
- **CDN 天然就近**：构建产物直接分发到全球节点，国内访问也比多数海外主机稳。
- **生态连贯**：Pages 负责静态页面，Workers 负责接口，D1 负责数据，R2 负责图片。付费阅读这种需要后端的功能，不用再单独找一台服务器。

## 这套方案的真实取舍

说点不好听的。静态站最大的问题是**任何动态能力都要自己补**：评论、搜索、付费、统计，在 WordPress 里是装个插件，在这里是写一个服务。所以我在这个博客上额外维护了一个 Worker 和一个 D1 数据库。

另外，静态站的「免费预览 + 付费解锁」不能靠隐藏 CSS 实现——那样正文其实已经下发到了浏览器。真正的做法是把付费部分根本不放进页面，单独存在数据库里，验证通过后再取回。这就是我下面几篇里会详细写的东西。

如果你也在犹豫要不要重建，我的建议是：写作量大于每月四篇，值得；只是想有个放文章的地方，用现成平台更省事。
